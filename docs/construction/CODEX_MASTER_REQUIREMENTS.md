# SmartRollator 总需求与硬约束

## 1. 事实源

- 产品边界：`docs/product/PRODUCT_REQUIREMENTS.md`
- 系统边界：`ARCHITECTURE.md` 与 `LAYER_CONTRACT.md`
- 当前真实状态：`DEV_PROGRESS.md`、`LOG.md`、`HANDOFF.md`
- 阶段验收：`CONSTRUCTION_PLAN.md` 和对应层级进度文档
- 用户最新明确指令可覆盖文档；覆盖后必须同步修正文档，避免双重事实源。

## 2. 重建原则

- 从当前仓库的完整参考基线出发，在阶段分支中按文件级施工树逐步替换为最小可验证工程；不把旧生成物与隐含状态直接认定为新基线。
- 旧代码仅用于提取协议、参数、行为和已知问题；迁移前必须复核。
- 先重建可观测的固定导纳基线，再接入 Hopf CPG；两者必须能独立测试和对比。
- 硬件未知参数不得静默猜测。允许临时占位，但必须有显式名称、保护性默认值和待确认记录。

## 3. 代码硬约束

- 工程目标 MCU 固定为 STM32H723VGT6，RTOS 为 FreeRTOS/CMSIS-RTOS2，除非产品负责人批准变更。
- 业务代码放在独立模块或 CubeMX USER CODE 区；自动生成区不直接编辑。
- 控制算法使用纯 C、固定宽度类型和显式单位，不依赖 HAL、RTOS 全局对象或打印函数。
- 驱动层负责字节和协议，控制层不解析 UART/CAN 原始帧。
- 任务间数据必须通过已定义的队列、消息或受控快照传递，不使用无说明的共享全局变量。
- 电机输出只允许经过唯一安全仲裁出口，禁止多个任务直接写驱动器目标值。
- 所有外部输入有时间戳、有效性和超时语义；所有计算有 NaN/Inf、范围和符号检查。

## 4. 安全硬约束

- 上电默认无驱动力；只有自检、通信和状态条件满足后才允许使能。
- 传感器超时、CAN 故障、任务失活、参数非法或急停触发时进入确定的安全状态。
- 调试日志、视觉数据和测试模式不得绕过速度/加速度限制与失能逻辑。
- 任何人体相关测试都在本项目 V1 范围之外；只能在受控台架、抬轮或等效安全装置下验证。

## 5. 质量与证据

- 阶段开始前写计划，阶段结束前跑测试并更新文档。
- “通过”必须能指向命令输出、构建日志、串口/CAN 记录或签字人工检查。
- 首次失败必须保留在 LOG，修复后追加复测结果。
- 没有测试时写“未建立”，不能以代码审阅替代运行测试。
- 文档、代码、测试和 Git 状态不一致时，阶段不能标记 Complete。

## 6. Git 硬约束

- 当前 Git 工作树的仓库根目录是唯一施工事实源；旧状态由 reference 分支和清单保留，旁路目录不得成为替代事实源。
- 每个有意义阶段开工前，必须有已推送的基线或备份分支。
- 精确暂存；禁止用 `git add .` 或 `git add -A` 混入无关文件。
- 默认禁止破坏性恢复和强制推送；恢复优先使用新分支、cherry-pick 或 revert。
- 提交信息描述一个可回滚的施工增量；推送后核对远端提交哈希。

## 7. 完成定义

阶段只有在交付物、测试、文档、Git 提交和远端备份全部满足时才可写 `Complete`。否则只能写 `Partially complete` 或 `Blocked`，并明确缺口与下一条可执行动作。
