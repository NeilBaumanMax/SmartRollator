# 施工工作流

本文件规定每次工作的执行闭环。docs 保存持久计划和进度，实际代码、检查证据与 Git 用于核实；聊天和 Agent 记忆仅提供线索。用户新指令改变范围时，先同步文档再继续。

## 1. 每次接续先读与核对

新任务、接续施工、恢复会话或上下文压缩后，按 [INDEX](../INDEX.md) 的每次必读项重新读取磁盘文件：AGENTS、开工入口、本工作流、总需求、当前阶段/节点、DEV_PROGRESS 最新计划及结论、HANDOFF、LOG 最新记录、当前层级。首次接手或范围变化补读产品、架构、契约、目录地图与 Files 索引。不中断的小增量无需每条命令重新读。

```sh
pwd
git rev-parse --show-toplevel
git status --short --branch
git remote -v
git log --oneline --decorate -8
git ls-files --others --exclude-standard
git ls-files --others --ignored --exclude-standard
```

确认 main 和当前仓库符合 HANDOFF；通过 fetch/ls-remote 核对远端，网络失败写明“未核对”，不能称同步。记录已有改动的来源与处理边界，不覆盖未知改动。文档与现场不一致时先核实事实、追加差异记录；旧日志保留原貌。

## 2. 先把本次计划写进 docs

修改代码前，在 [DEV_PROGRESS](DEV_PROGRESS.md) 追加日期、当前阶段/节点、目标、已读记录、仓库状态、拟改文件/接口、验收检查、Git 基线、远端备份、回滚方式、排除项。可用 [开工模板](templates/PHASE_START_TEMPLATE.md)。小任务只需一个短条目，不重复建立另一套施工文档。

有意义的代码重建前，必须存在并核对已推送的备份分支。没有远端恢复点时先完成备份。产品/架构/接口变化先改相关需求、契约、施工树与决策，再编码。仅续做同一计划也要留下本次起点和剩余范围。

参数变化记录来源、单位、旧值、新值和验证依据；生成代码变化保留 .ioc 事实源并记录生成器/固件包版本及清单。先建立可观测性，再接通输出；先检查纯逻辑，再进入目标板和台架验证。

## 3. 小步实施与 STM32 自检

```text
一个内聚改动 → 检查改动及调用方 → 记录结果/失败/修复/复测 → 下一个改动
```

普通 STM32 代码增量可按用户要求以静态代码自检作为本次验收，不要求每次连接硬件或强行建立测试框架；自检内容和证据边界见 [TEST_METRICS](TEST_METRICS.md)。现有适用检查继续使用；生成、编译、硬件验收节点仍需对应真实证据。

发现问题先修复并复查；LOG 保留首次失败的命令或审阅步骤、实际错误、原因、修复和复测。没有执行的检查如实写 Not run，未建立的入口写 Not established。不以“生成成功”或“看起来正确”代替编译/硬件结果。

## 4. 修正文档漂移并交接

对照实际 diff 检查：需求和范围、目录/路径、接口/依赖、参数单位、工具命令、当前节点完成度、验证状态、Git 分支和下一步。决定纠正代码还是文档，记录依据并复查受影响项。

每个增量结束都更新：

- DEV_PROGRESS：本次计划的实际完成项、剩余项与状态，不改写历史计划冒充全部完成。
- LOG：改了什么、查了哪些文件/边界、实际结果、首次失败/修复/复测、漂移处理。
- HANDOFF：最新状态、未完成、验证边界、下一步具体动作和相关文件、Git 基线/备份、交付状态。
- 当前层级及受影响需求/施工树/目录索引：仅更新实际改变的事实。

交接验收：一个没有聊天历史的 Agent 能否只读 docs 找到下一步并避免重复已完成工作？如果不能，补齐交接。主动中断前也记录已做/未做、待提交路径和恢复动作；意外中断后核对 diff 再补记，不能猜测上轮结果。

## 5. 提交、漂移复核、推送

1. 完成适用检查和文档同步，执行 `git diff --check`，审阅所有待提交路径。
2. 按既有全部文件备份要求核对 tracked/untracked/ignored；有文件变化就刷新 [当前快照清单](../verification/workspace-backup/files.sha256)，保留历史归档清单。未知文件先归属确认，敏感内容不静默上传。
3. 精确暂存并检查 `git diff --cached --check`、staged diff；提交一个可解释、可回滚的增量。
4. 提交后再次核对文档与实际提交。如果先完成了代码提交，再产生漂移修正，就追加文档提交并复查；不能把修正文档留在未提交工作树中便推送结束，也不为改文字改写旧提交。
5. 普通推送到当前 main，核对 `git rev-parse HEAD` 与 `git ls-remote origin refs/heads/main` 一致，并检查工作树、未跟踪与忽略项；失败则保留本地提交，记录原因和下一步，不报告已推送。
6. 最终报告本次状态、实际检查、未运行项、提交哈希和远端核对结果；本次增量完成不等于整个 Phase 完成。

文档中的 Git 字段区分“已核实的上一交付”与“本轮待执行动作”；最终提交及远端状态以 Git 实时查询为准。不要预写成功，不为把提交自身哈希写回自身而无限追加提交；下次接续记录上次实际交付哈希。若推送失败，更新 LOG/HANDOFF 并在恢复后补交文档。
